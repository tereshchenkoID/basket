# Модель доступа Basket v0.2

## Доверенные границы

Browser/server Supabase clients используют только Publishable key и текущую пользовательскую сессию. Server Actions проверяют `getUser`, разбирают вход через доменную Zod-схему и вызывают RPC. Клиентские ограничения дополняют UX; PostgreSQL остаётся источником прав.

Прямые REST/SQL записи через `authenticated` в группы, участников, приглашения, списки и товары запрещены GRANT-правами. Для профиля разрешены только `display_name` и `avatar_url`, с RLS по своему UUID. Даже ручная подмена JSON REST-запроса не даёт назначить `created_by`, перенести запись или повысить роль.

## RPC и SECURITY DEFINER

Операции, обходящие read-only таблицы, обязаны самостоятельно авторизовать действие. Поэтому mutation RPC используют `SECURITY DEFINER`: это единственный путь записи, без параллельного небезопасного REST API.

| Функции                                                                                 | Проверка                                                                                      |
| --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `private.is_member`, `private.is_owner`                                                 | Членство только для `auth.uid()`, активная строка без `removed_at`                            |
| `create_group`                                                                          | Подтверждённый UID, атомарно группа + владелец + список, повтор UUID только владельцем        |
| `rename_group`, `create_group_invite`, `revoke_group_invite`                            | Только владелец соответствующей группы                                                        |
| `remove_group_member`                                                                   | Владелец удаляет участника или участник удаляет себя; владелец не выходит                     |
| `group_member_profiles`                                                                 | Только активный участник; минимальные имена/аватары/роли, без email                           |
| `preview_group_invite`, `accept_group_invite`                                           | Подтверждённый UID, корректный hash/срок/отзыв/лимит; preview раскрывает лишь название группы |
| `create_shopping_list`, `update_shopping_list`                                          | Активное членство в группе списка                                                             |
| `add_shopping_item`, `edit_shopping_item`, `set_item_purchased`, `delete_shopping_item` | Активное членство и активный список, блокировка списка и membership на время записи           |
| `private.handle_new_user`                                                               | Trigger от `auth.users`; EXECUTE полностью отозван у публичных ролей                          |

Все definer-функции закрепляют `search_path = ''`; таблицы квалифицированы. Доступные RPC выданы только `authenticated`, не `anon` или PUBLIC. Вспомогательные мутации и triggers недоступны для прямого вызова. UUID целевого участника в удалении не считается личностью вызывающего: субъект всегда определяется `auth.uid()`.

Уникальный partial index ограничивает владельца одной строкой. Только `create_group` может её создать; изменить роль или удалить владельца публичные операции не позволяют. FK `groups.created_by` блокирует удаление auth-владельца с сохранённой группой.

## Приглашения и конкуренция

Server Action генерирует `randomBytes(32).toString('base64url')`, сохраняется только SHA-256. Открытый токен возвращается только владельцу при создании. Потерянная ссылка не восстанавливается из БД; можно отозвать её и создать новую.

Принятие блокирует строку приглашения `FOR UPDATE`, проверяет ограничения и добавляет участника/увеличивает use_count в той же транзакции. Второй конкурент не может превысить лимит. Повтор действующего участника не расходует ещё одно использование и не создаёт вторую membership. Повтор после удаления требует нового пригодного приглашения.

Операции создания групп/списков/товаров используют operation UUID и advisory transaction lock. Повтор не вставляет новую строку; совпавший UUID чужой операции не позволяет изменить её или раскрыть данные. Покупка задаёт желаемый boolean, не инвертирует состояние в БД. Аудит покупки назначается базой и очищается при снятии отметки. Редактирование товара не переписывает отметку; переименование списка не переписывает статус архива.

## Realtime и soft delete

RLS не фильтрует DELETE так же, как INSERT/UPDATE. Поэтому товары удаляются через `deleted_at`, а membership отзывается через `removed_at`. Интерфейс исключает удалённые товары. Отозванный пользователь может прочитать только свою membership-строку, чтобы получить scoped UPDATE. Другие данные группы остаются недоступными на уровне БД.

Групповые каналы фильтруют group_id; товарный канал фильтрует list_id. На dashboard фильтр membership равен user_id. Нет широких подписок на всю БД. После события/reconnect UI перечитывает снимок с сервера через RLS; payload не считается разрешением или источником истины. При отключённом Realtime права всё равно соблюдает база.

## Логи и кеш

Не добавляйте auth codes, auth tokens или invitation tokens в логи. Next dev incoming-request logging исключает пути/query с `invite` и OAuth callback. Referrer-Policy — no-referrer. Это не настраивает внешние reverse proxy / CDN / analytics: на каждом хостинге исключите invite URL и callback/login query из access-логов отдельно.

Приватный HTML и callback не кешируются. Logout использует cookie API Next.js, инвалидирует Router Cache и возвращает login. Сессия текущего браузера завершается без выхода из всех остальных устройств.
