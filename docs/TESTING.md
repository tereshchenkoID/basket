# Проверки Basket

## Автоматические

```sh
npm ci
npm run check
npm run test:db
npm run build
npm run start
# Второй терминал:
npm run test:smoke
```

`check` включает ESLint и Stylelint с `--max-warnings=0`, TypeScript и unit-тесты. За форматирование отвечают stylistic-правила линтеров из Betman. SCSS проверяется целиком, включая `src/scss/globals.scss`; порядок CSS-свойств соответствует Betman, классы ограничены kebab-case. Проверяются redirect/locale/invite allowlists, origin, Zod-нормализация, положительное количество, единицы и полнота четырёх словарей.

`test:db` запускает настоящий изолированный PostgreSQL 17 из dev dependency `embedded-postgres`, применяет миграцию и создаёт несколько пользователей с отдельными подключениями под `authenticated` / `anon`. Docker и облачные credentials не нужны. Порт по умолчанию 55439; при конфликте задайте `BASKET_TEST_PG_PORT`. Кластер и тестовые данные удаляются после теста. Для запуска требуются права на локальный процесс и loopback socket.

Если npm блокирует postinstall тестового PostgreSQL, harness использует `autoRehydrateSymlinks` для восстановления необходимых symlinks внутри npm-пакета. Не включайте глобально все install scripts ради этого теста.

Проверки базы:

- trigger/backfill профилей и доступ только к своему профилю;
- запрет анонимного доступа и закрытые функции;
- атомарная группа с единственным владельцем и первым списком, retry без дублей;
- скрытые чужие группы/списки/участники и запрет прямых записей ролями REST;
- запрет назначения себе владельца, чужих приглашений и удаления владельца;
- hash-only хранение приглашений, preview без раскрытия списков, идемпотентное принятие;
- истёкшие, отозванные, фиктивные и использованные приглашения;
- одновременное принятие одноразового приглашения двумя соединениями;
- валидация количества/названий/единиц и запрет подмены атрибуции/родителя;
- конкурентные retry добавления товара и намеренные одинаковые названия;
- покупка/снятие отметки и аудит, параллельные правки двух пользователей;
- независимое изменение названия/статуса списка, read-only архив;
- отзыв доступа, новое приглашение после удаления и добровольный выход;
- RLS всех таблиц, фиксированный search_path и ограниченная публикация Realtime.

Это проверка реальной PostgreSQL и прав БД. Только `auth.uid()` / `auth.users` создаются test harness как адаптер JWT-контракта Supabase. PostgREST и Realtime gateway этим тестом не запускаются. Успешные SQL-тесты не выдаются за проверку браузерной синхронизации.

HTTP smoke требует запущенную Next production-сборку и настроенный `.env`. Он выполняется без cookies и проверяет все языки, защиту dashboard/group/list, 404 неверных путей и безопасные отказы приглашений/callback. Адрес проверяемого сервера задаётся через `TEST_BASE_URL`. Если production-сборка запущена на другом локальном порту, задайте `TEST_AUTH_ORIGIN` равным доверенному `NEXT_PUBLIC_SITE_URL`: callback обязан использовать конфигурацию приложения, а не origin тестового запроса.

## Перед облачным демо

1. Выполните CLI login/link/dry-run/push из README. Убедитесь в применённой миграции, RLS и таблицах публикации `supabase_realtime`.
2. Используйте два Google-аккаунта A и B в отдельных браузерных профилях / на разных устройствах. Для локального теста с телефоном нужен доступный HTTPS deployment либо соответствующая конфигурация origin; `localhost` телефона не указывает на компьютер.
3. A создаёт группу; сразу видит себя владельцем и первый локализованный список. Создайте вторую группу и убедитесь в независимости данных и счётчиков dashboard.
4. A создаёт приглашение; B открывает ссылку без сессии, проходит Google OAuth, возвращается к приглашению на том же языке и подтверждает вступление. До подтверждения B не должен видеть участников или списки группы.
5. Откройте один список у A и B. Добавляйте товары, меняйте количество/единицы/название, отмечайте и снимайте покупки, удаляйте. Изменения должны появляться у второго без reload и без дублей. Переключение языка должно сохранять группу и список.
6. Сделайте быстрый двойной submit и повтор после сетевой ошибки. Один и тот же operation ID не должен создавать второй товар; намеренно добавленные одинаковые названия должны оставаться отдельными.
7. Отключите сеть B, измените список у A, восстановите сеть B. Должны восстановиться канал и актуальный серверный снимок. При возвращении к фоновой вкладке снимок перечитывается.
8. A удаляет B, пока B держит группу/список открытым: интерфейс B должен перейти в состояние отсутствия доступа; повторный запрос/мутация должны быть запрещены. Повторите с offline B и возвратом online.
9. Проверьте отозванную и использованную ссылку третьим пользователем. Для проверки срока в тестовой среде используйте тестовый expired fixture в SQL harness; не меняйте реальную дату устройства или production-ограничения.
10. Архивируйте список: товары становятся read-only. Восстановите его, проверьте совместную работу.
11. B добровольно выходит из группы. Владелец не может покинуть её. Участник не может переименовать группу, создать приглашение или получить чужой список по UUID.
12. Проверьте Google logout, reload и Back, а также запись пользователя в Supabase → Authentication → Users.

Для прямого REST smoke можно использовать publishable key и access token именно тестового пользователя в собственной защищённой сессии. Не сохраняйте пользовательские tokens в исходники, `.http`-файлы, shell history или отчёты. Ожидается запрет POST/PATCH в таблицы и ограниченный SELECT; вызовы RPC также проверяют членство. Серверные service_role credentials для этой проверки не подходят.

## Состояние проверки 3 ноября 2026

- `npm run build`: production-сборка прошла; временного QA-маршрута в ней нет.
- `npm run test:smoke`: все четыре языка, защита dashboard/group/list и безопасный OAuth-возврат к приглашению прошли на production-сборке.
- `npm run check`: ESLint без предупреждений, TypeScript и 11 unit-тестов прошли.
- `npm run test:db`: 10 интеграционных сценариев (11 записей Node test runner вместе с родительским тестом) прошли на PostgreSQL 17.
- Визуальные проверки на 320 px: карточки групп, группа, список и форма редактирования товара без горизонтального overflow. Использованы временные fixtures; маршрут удалён перед production build. Это проверка вёрстки, не облачной синхронизации.
- `npm ci --dry-run --ignore-scripts --offline --no-audit`: lockfile согласован, конфликта зависимостей нет.
- `npm audit --omit=dev`: 0 уязвимостей. Полный audit сообщает 18 moderate записей в dev-цепочке ESLint из-за транзитивного minimatch (GHSA-g3hv-75wg-m249). Не применять автоматически `audit fix --force`, предлагающий несовместимое понижение инструментов; обновления проверять вместе с Next ESLint plugins.
- В исходниках не обнаружены secret keys / private keys / JWT. `.env` и временные файлы CLI исключены из Git.
- Облачная миграция не применена: CLI вернул `AccessTokenRequiredError`. Google-вход по приглашению, PostgREST и Realtime между двумя настоящими устройствами остаются обязательной ручной проверкой после применения миграции.

## Исправление при сохранении в WebStorm

В проектных настройках IDE уже включены `fix-on-save` для ESLint и Stylelint. Для ручного исправления используйте независимые команды:

```sh
npm run lint:fix
npm run stylelint:fix
```

Stylelint исправляет доступные автоматические нарушения: например, порядок свойств и пустые строки. Неисправимые нарушения остаются в диагностике; команда при этом завершается ненулевым кодом, но исправления записываются. Имена классов автоматически не переименовываются, чтобы не нарушить ссылки из JSX. Если SCSS не разбирается из-за пропущенной скобки/некорректной декларации, сначала устраните синтаксическую ошибку. Проверка `npm run stylelint` работает без изменения файлов; `stylelint:fix` — с `--fix`.
