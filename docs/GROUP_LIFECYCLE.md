# Группы, вкладки и срок хранения

Группа мягко удаляется владельцем через `delete_group`; `restore_group` возвращает её до истечения ровно 720 часов. Повтор одинаковой операции безопасен. При удалении приглашения отзываются атомарно и не оживают при восстановлении. Участники, списки, покупки и статусы архивов сохраняются. Выход участника использует существующий `remove_group_member`; владелец выйти не может.

## Миграции

- `20261105000100_group_lifecycle.sql`: `groups.deleted_at`, индекс очистки, `group_members.revision`, RPC удаления/восстановления, усиленные проверки доступа, закрытая функция очистки.
- `20261105000200_group_cleanup_schedule.sql`: включает `pg_cron` и создаёт активное задание `basket-purge-deleted-groups` каждые 10 минут. Ошибка установки расширения прерывает эту миграцию, а не оставляет очистку ненастроенной.

Перед выкладкой приложения применить обе миграции к нужному проекту:

```sh
supabase db push --remote --dry-run --skip-vault
supabase db push --remote --skip-vault
```

Cron удаляет до 100 истёкших групп за запуск, с `FOR UPDATE SKIP LOCKED`. FK каскадно удаляют membership, приглашения, списки и товары. Активные и недавно удалённые группы сохраняются. Восстановление блокируется базой сразу по истечении срока, даже до следующего запуска Cron.

Проверка в Supabase SQL Editor / Database → Cron:

```sql
select jobid, jobname, schedule, active, database, username
from cron.job where jobname = 'basket-purge-deleted-groups';

select d.status, d.start_time, d.end_time, d.return_message
from cron.job_run_details d join cron.job j using (jobid)
where j.jobname = 'basket-purge-deleted-groups'
order by d.start_time desc limit 10;
```

Наличие файла миграции не означает, что задание уже работает в конкретном окружении: проверить применение миграции, `active = true` и историю запусков. Новые environments требуют тех же двух миграций.

## Права и синхронизация

Существующие RLS `groups_member_read`, `lists_member_read`, `items_member_read`, `invites_owner_read` усилены общей проверкой: `is_member`/`is_owner` теперь требуют активную группу. Удалённую группу нельзя прочитать даже владельцу через обычный SELECT. Проверенный `dashboard_groups` возвращает ему только карточку восстановления; участники и посторонние не получают её.

`assert_writable_list` проверяет активность группы. Дополнительные triggers на записи в дочерние таблицы блокируют запись после удаления, включая гонку между RPC и удалением. Все definer-функции закрепляют пустой `search_path`; новые публичные RPC доступны только `authenticated`, очистка — только административному владельцу функции/Cron.

Изменение `deleted_at` увеличивает `revision` у действующих membership. Собственную строку пользователь продолжает читать по существующей RLS, поэтому scoped UPDATE остаётся доступен после потери доступа к группе. Hook сохраняет Postgres Changes и `router.refresh()`, дополнительно обновляет видимую страницу каждые 30 секунд, при фокусе и возвращении online. Отказ записи по правам также вызывает refresh. Payload не используется как источник данных или разрешений.

## Интерфейс

- `/[locale]/dashboard?tab=active|deleted` — группы; по умолчанию active.
- `/[locale]/groups/[group-id]?tab=active|archived` — списки.
- Неизвестное значение вкладки возвращает active. Native History API интегрируется с `useSearchParams`, поддерживает back/forward и сохраняет введённые формы вне панелей. Смена языка сохраняет query выбранной вкладки.
- Сортировка независима для каждой вкладки; при равных значениях используется `id`.
- Архивные списки сортируются как «недавно обновлённые», поскольку `updated_at` не считается датой архивации. Новое поле ради этого не добавляется.
- Общий `Tabs` находится в `components` и dev-каталоге. Controlled/defaultValue, disabled, счётчики, панели, ARIA-связи, стрелки/Home/End и горизонтальная прокрутка.

## Проверки

```sh
npm run check
npm run build
```

UI kit позволяет вручную проверить controlled state, ARIA, клавиатуру и мобильный экран.

Для проверки Realtime нужны две авторизованные сессии: участник открывает список, владелец удаляет группу; участник должен получить экран недоступности. После восстановления доступ возвращается без приглашения. Архивирование и восстановление списка также должны отображаться в обеих сессиях.

Обе миграции применены к production-проекту `basket`. Cron активен, успешный запуск подтверждён в `cron.job_run_details`. Проверку Realtime с двумя пользователями пользователь проводит самостоятельно.
